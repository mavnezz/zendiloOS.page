Features in detail

Storage and disks

Your data on ZFS, with guard rails.

zendiloOS keeps your data on OpenZFS, which checks every block it reads and repairs it from a second copy where the layout has one. A pool is one or more disks in one layout, and zendiloOS tells you what each layout survives before you choose.

Disks are known by their serial numbers, never by names such as sdb that can change. Before a pool is created or deleted, a plan lists every disk that will be erased, and the pool’s name has to be typed again; the agent checks once more before it touches a disk.

In the documentation:Storage conceptGuard rails
Layouts
A single disk, a mirror (2 disks or more), RAIDZ1 (3 or more), RAIDZ2 (4 or more), RAIDZ3 (5 or more)
Defaults
lz4 compression, access times off, 4K sectors; each pool mounted as a volume
Checks
SMART every six hours, short and long self-tests on a schedule, a scrub every month and whenever you start one
Where each disk sits
Bays from a catalog of NAS models or a layout of your own, a disk that blinks to be found, purchase date and warranty for every disk
New pool
A wizard in three steps: disks and layout side by side with the usable space, speed and protection estimated, a name, then the plan to confirm
Pools of an earlier installation
Found and imported when you ask, never by themselves: a pool another machine still uses would be damaged
Tested
In virtual machines: a mirror built, a disk pulled out and replaced, resilver, scrub, deletion refused while shares, Docker or VMs live on the pool. The bay order of the built-in NAS models is not yet confirmed on the real machines.

Shares and files

A shared folder for every device in the house.

A share is a folder on a volume with a ZFS dataset of its own. You decide for each person and group who may read or write, and Samba, NFS and the file explorer hold everyone to the same rule. Windows finds the NAS through WS-Discovery, macOS through Bonjour.

Snapshots keep earlier states of a share, taken by hand or on schedules, and Windows offers them as previous versions. The explorer in the browser reaches personal folders, shares and USB drives in one window.

In the documentation:Share and file permissions
Protocols
SMB from version 2.0 on, never SMB1; NFS. Each switched on or off as a whole
Access
Read and write or read only, for each person and group; NFS for each computer or network
Per share
A quota, compression (lz4, zstd or off) and the record size
Snapshots
Hourly, daily, weekly and monthly, each keeping 1 to 100; files copied back out of them; a share rolled back with its name typed again
Recycle bin
One for all folders in the explorer; deleting over SMB or NFS is final, and the snapshots keep what was there
Explorer
A tree of folders, drag and drop, uploads, folders downloaded as archives, a search through every subfolder
USB drives
FAT, exFAT, NTFS and ext4: mounted, copied from and to, ejected
List and grid
Large icons in a grid, a toolbar with the actions, the sidebar in sections
Tested
With real SMB and NFS clients inside a virtual machine. No Windows or macOS computer has used a share yet.

Apps and Docker

Apps in a click, and yours to change.

The App Center installs apps from the community catalog or from catalogs you add. You choose an app’s folder, ports and settings and see its compose.yaml before it starts; from then on it is an ordinary Docker Compose project of yours, changed, updated and removed in the Docker app.

Whatever reaches beyond a container, such as a device, the host’s network or the Docker socket, is named and needs your consent. Docker itself is a plugin of the App Center, from Debian’s own packages, installed when you need it.

In the documentation:Apps and Docker
Catalogs
The community catalog built in; others added from a GitHub repository or an address
Consent
Devices, the host’s network, the Docker socket and folders of the host named before a project starts
Docker app
Containers, images, networks and Compose projects; a page for every container with its live log and a terminal
Image updates
Containers with a newer image marked, updated from the list or on a schedule
Volumes
Listed with the containers that use them, backed up into a share daily, weekly or monthly, restored under their name or into another volume
Plugins
Docker, certificates from Let’s Encrypt; virtual machines and Backup
Architectures
Each app says which architectures its images are made for; one that has none for your machine cannot be installed
Tested
In virtual machines: Docker installed as a plugin, projects with consent, the terminal, image updates, volumes backed up and restored, an app from the catalog becoming your own project.

Virtual machinesPreview

Virtual machines beside your data.

The Virtual machines plugin of the App Center brings libvirt and QEMU from Debian and an app in which administrators create, change, start and stop VMs. A VM can have several disks and network cards, its ISOs come from an image library, and its console opens in the browser.

Snapshots take all of a VM’s disks at once, by hand or on schedules. Backups go into a share or onto a USB drive and are restored as a new VM or over the old one. For Windows 11 a VM gets a TPM and Secure Boot.

Virtual machines are a preview, on x86-64 only. The plugin first checks that the processor can run them (Intel VT-x or AMD-V).

In the documentation:Virtual machines
Hardware
Up to 8 disks (virtio or SATA), up to 4 network cards (virtio or e1000e), up to 3 drives for ISOs; UEFI or BIOS
Presets
Linux, Windows (with TPM and Secure Boot) and other
Networks
Through the NAS, on a bridge, directly on a network card (macvtap), or on an internal network that the NAS itself stays off
Storage
Disks as ZFS volumes on one or more pools; each pool shows its health, its space and the VMs on it
Images
ISOs copied from a share or uploaded from the browser
Console and load
The console in the browser (noVNC); processor and memory of every VM live
Snapshots
All disks at once, the guest’s file systems frozen if its QEMU guest agent answers; hourly, daily, weekly or monthly; rolled back while the VM is off
Backups
Every disk compressed with zstd and checked by its checksum when restored
Host devices
USB devices, also while the VM runs; PCI devices with an IOMMU and the VM off. Devices the host needs, such as the controller of its disks, are refused
Tested
In nested virtual machines: VMs with several disks and cards, the image library, the console, snapshots compared by checksum, backups restored, a TPM and Secure Boot. Not yet: devices handed through on real hardware, and a Windows 11 installation.

Backups

A second copy, somewhere else.

ZFS protects your data from a failing disk, not from a deleted folder, a fire or a theft. The Backup plugin brings rsync and rclone from Debian and an app in which administrators set up backup tasks: from a share to another pool, a USB drive, a server or a cloud, on a schedule or whenever the drive is plugged in.

Every run is a job with its log and its list of files, and a failed or partial run is notified. A restore takes all or some of a version, back to where it came from or into another folder.

In the documentation:Backup
Targets
Another share or pool, a USB drive, an rsync server through its daemon or over SSH with the server’s host key pinned, Google Drive, OneDrive
From a server
A folder of a server backed up into the NAS
Mirror or versions
A mirror, optionally keeping what a run deletes or replaces for some days; or dated versions, unchanged files hard-linked to the version before, kept by number and age
Encryption
Names and contents encrypted with rclone’s crypt, to a share, a drive, a cloud or an SSH server
Schedules
Hourly, daily or weekly in the NAS’s time zone, or when the drive is plugged in
Isolation
Every run in a unit of its own that sees only its folders and writes only to its target; passwords and keys never on a command line; Google Drive asked only for the files the NAS writes
Also backed up
Docker volumes into a share; virtual machines into a share or onto a USB drive; the configuration, under Updates and recovery
Tested
In virtual machines: mirrors and versions between pools, a USB drive, an rsync daemon and SSH, restores, an encrypted backup. Google Drive and OneDrive only against stand-ins: no backup has gone to a real account yet.

Network

Network changes that wait for your confirmation.

Each network card gets its addresses by DHCP or fixed, IPv6 from router advertisements, and up to three name servers. zendiloOS manages the network through systemd-networkd, now also on installations from the ISO, and takes over a Debian set up with ifupdown when you ask.

A change is kept only once you confirm it within two minutes, from the new address if it changed; otherwise everything goes back by itself. Changes made outside zendiloOS, at the console for instance, are noticed, and you choose whether zendiloOS restores its settings or keeps the files.

In the documentation:Network
Per card
IPv4 by DHCP, fixed or off; IPv6 from router advertisements or off; up to three name servers
Confirmation
Two minutes to confirm from the browser, or the change goes back; switching a card off asks first
Bridges
Wired cards, bonds and VLANs as members, or none for VMs only; STP off unless asked
Bonds
Active-backup, 802.3ad (LACP) or balance-alb
VLANs
IDs 1 to 4094, on a card, a bond or a bridge
ISO and ifupdown
Installations from the ISO managed from the first start; a Debian with ifupdown taken over on request, what cannot be taken over named with its file, line and reason, and left as it is
Outside changes
A notification and a note on the Network page, then restore or keep the files
The machine’s name
Changed from the interface, up to 15 characters; SMB, mDNS (name.local) and WS-Discovery follow, and the machine’s own certificate is made anew
Tested
In virtual machines: addresses changed, a change that cuts the machine off going back, the takeover from ifupdown confirmed and not, bridges, bonds and VLANs.

Security

Nothing changes without a check.

The web interface and its API run without privileges. Whatever changes the system goes through zendiloos-agent, a small, sandboxed service that checks every request against strict rules and runs the tools with fixed arguments.

Signing in can ask for a code from an authenticator app, failed attempts block the address for a while, and every session can be ended. The firewall decides who reaches which service, Docker’s published ports included, and a change to it goes back unless you confirm it.

In the documentation:Security modelLicenses
Sign-in
Two-factor with an authenticator app, recovery codes, a password policy, limits on failed sign-ins and blocked addresses
Roles
Administrator, user and read only; the server checks every request, whatever the interface shows
Firewall
nftables, rules by service, address or network, Docker’s published ports included; a change goes back after 90 seconds unless confirmed
HTTPS
TLS 1.2 or newer; the machine’s own certificate, or one from Let’s Encrypt through HTTP-01 or DNS-01
DNS providers
81 for DNS-01, from dynamic DNS services such as IPv64 to hosters and large clouds, each checked against Debian’s acme.sh
SSH
Switched on for a job, with its port and who may log in; it switches itself off again after up to a day
Audit log
Every change by an administrator recorded; searched and exported as CSV
Releases
Signed with minisign and verified before they are installed
Software bill of materials
CycloneDX for every package of a release, and the licenses of everything it contains
Tested
In virtual machines: TLS, failed sign-ins and blocked addresses, sessions, two-factor sign-in, the firewall with Docker’s ports, SSH switching itself off, certificates through ACME.

Updates and recovery

Updates without surprises, and a way back.

Once a day zendiloOS looks for Debian’s package updates and for new releases of zendiloOS on your channel. You decide when to install them, a release is installed only with a valid signature, and the NAS restarts only when you say so.

ZFS is built for each kernel. A kernel whose ZFS module could not be built is never started: GRUB keeps starting the newest kernel that has it, and the Updates page says which one starts next and why.

A configuration backup keeps accounts, shares, settings and certificates in one file encrypted with a passphrase. Restored on a fresh installation instead of its first setup, it brings the machine back: the old installation’s pools are imported when you ask, and its network and firewall settings are applied one by one, each confirmed.

In the documentation:Releases and channelsConfiguration backup and recovery
Channels
Stable for releases, test for release candidates too, development for every change; a NAS takes only a version newer than its own
Signature
minisign over the checksums; the signature names the version, and a NAS takes a test or development build only on that channel
Downloads
Tried up to four times when GitHub does not answer
Configuration backup
Encrypted with age and a passphrase of at least 12 characters; downloaded, or daily or weekly into a share or onto a USB drive, the newest kept
Restore
In the first setup or later; the whole file checked before anything changes; pools imported on request; network and firewall applied only once confirmed
Rescue
“Rescue a zendiloOS system” in the ISO’s boot menu: a shell in the installed system, to copy a backup off a machine that does not start or to repair it
Still to come
A recovery entry in the installed system’s boot menu, and a live image with ZFS for a machine whose system disk is gone
Tested
In virtual machines: updates of Debian and zendiloOS, refusals, a kernel without ZFS never started, an older installation upgraded with its data, a configuration backup restored on a fresh machine and its pool imported.

Monitoring and notifications

Trouble told before it grows.

Widgets on the desktop and the resource monitor show processor, memory, network and disks over time. zendiloOS looks at the pools every minute and at the disks’ SMART values every six hours, and tells you when something changes.

Notifications reach you in the browser, by e-mail through a mail server you name, and by webhook, chosen for each kind. One that cannot go out because the network is not up yet is tried again later.

In the documentation:Monitoring
Channels
In the browser, by e-mail through one mail server, by webhook; chosen for each kind
Storage
A pool degraded or recovered, a resilver or scrub finished, a volume 80 or 90 % full, a disk’s SMART values getting worse
eMMC
The wear of an eMMC system disk, which has no SMART, as on single-board computers such as the ZimaBoard
Delivery
A queue that survives restarts: tried again from a minute up to an hour apart, for about twelve hours
Fewer writes
Requests that only read logged at debug level only, the journal kept to 512 MiB, systemd reloaded only when something changed
Tested
In virtual machines: e-mail and webhook, a delivery tried again once the receiver is back, also across a restart.

Hardware and architectures

From a mini PC to a NAS board.

zendiloOS runs on Debian 13. On x86-64 that is a NAS appliance, a mini PC or a machine of your own, with UEFI or a BIOS. It needs a disk for the system, one or more disks for data (SATA or NVMe) and a network connection: the installer fetches Debian’s packages from its mirror.

zendiloOS is now built for arm64 too: packages, and an installation ISO that starts through UEFI, for NAS boards and single-board computers whose firmware starts a USB stick through UEFI and whose hardware Debian’s own kernel supports. Boards that need their vendor’s kernel do not work.

zendiloOS is tested end to end in virtual machines. On real hardware it has run only on one small x86-64 board so far, and no real arm64 board has run it yet.

In the documentation:HardwareTesting on arm64What is not tested yet
x86-64
UEFI or BIOS; the ISO has both boot menus and the graphical installer
arm64
UEFI only (EDK2 or U-Boot’s), the text installer, which a serial console shows too; built and its tests run on arm64 in CI; not yet tried on a real board
Virtual machines
On x86-64 only, with Intel VT-x or AMD-V; PCI devices need an IOMMU
Installer
Debian’s own, with six questions: language, location, keyboard, name, root’s password and the system’s disk, which is never chosen for you
A release holds
The packages, signed checksums and the installation ISOs; packages and an ISO for arm64, and a software bill of materials for each package
NAS models
Bay layouts of known models, the UGREEN DXP4800 Plus first, not yet confirmed on the real machine
Tested
The installation from the ISO, unattended in a fresh virtual machine. On arm64 the backend’s tests run natively; the emulated installation has not been run to its end yet.
